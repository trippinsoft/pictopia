# About this app

This file describes this app's stack, structure, and conventions. **Keep it updated and short**: when the app gains a backend, new conventions, or significant structure, edit this file (and the README) in place so future sessions inherit that knowledge. This file is loaded into every session, so it describes the current state only. Never add dated or per-task entries, change logs, or test results, even if earlier ones exist. Put notable decisions in `docs/HISTORY.md` as one line each, and keep this file under about 200 lines.

## Stack

- Expo cross-platform app (iOS / Android / Web), TypeScript (strict), Expo Router (file-based routing under `app/`)
- NativeWind (Tailwind for RN) for styling
- Yarn Berry (v4.x) — check `.yarnrc.yml` for the linker; with Plug'n'Play there is no traditional `node_modules`. Patching dependencies is a last resort; use `yarn patch`, never hand-edit.
- React Query available for server state when a backend is wired
- Path aliases are defined in `tsconfig.json` `paths` — use them instead of long relative imports.

## Theming

Keep colors and typography centralized in the app's existing theme setup (Tailwind config, theme files, or CSS variables) and use them through NativeWind classes — never hardcode per screen. When changing colors/typography, update the central definitions. Support both light and dark with readable contrast if the app supports both.

## Conventions

- **Reuse first:** use the app's existing component, icon, and styling libraries and patterns before adding new ones. Check `package.json` and existing components before introducing a dependency.
- **Icons:** use the app's existing icon approach. If icons need NativeWind classes, make sure they go through a wrapper or interop that applies them.
- **Navigation:** set an explicit human-friendly `title` for every screen header — never let route names like `(tabs)` or `products/[id]` appear in the UI. Keep `app/index.tsx` for redirects, not feature UI; use `_layout.tsx` files for stacks/tabs.
- **API routes:** server-only logic can live in Expo Router API routes (`+api.ts` files under `app/`). They require `web.output: "server"` in the app config and run in the preview; secrets they read use unprefixed environment variables, never `EXPO_PUBLIC_`.
- **Fonts:** load through the `expo-font` config plugin (declared in the app config) or `useFonts` in the root layout — follow whichever the app already uses.
- **Screens:** wrap in SafeAreaView (react-native-safe-area-context) and handle scrolling/gestures correctly. Keep bottom tab bars compact — pad content inside screens, not via `tabBarStyle`.
- **Components:** keep components small and focused, follow the app's existing folder structure, and reuse before creating.
- **Performance:** `FlatList`/`SectionList` for long lists — never `ScrollView` + `.map()` for large collections.
- **Press feedback:** `active:`/`hover:`/`focus:` classes go only on the `Pressable` itself, never on a plain `View`/`Text` inside it — NativeWind upgrades such a View to its own Pressable on native, which claims the tap and the real `onPress` never fires (works on web, dead on device).

## Draftbit starter structure (if present)

Apps created from the Draftbit starter ship with the pieces below. Follow them where they exist; don't add them to apps that don't have them.

- **Theming:** `theming/ThemeProvider.tsx` injects theme objects (colors + typography) as CSS variables via NativeWind's `vars()`; typography is flattened (`h1.fontSize` → `--h1-fontSize`). Theme shape in `theming/Theme.ts`, concrete themes in `theming/themes/light.ts` and `dark.ts`, mapped to classes (`text-foreground`, `bg-background`, `text-h1`, `border-border`, …) in `tailwind.config.js`. `lib/useColorScheme.tsx` syncs the system preference. Use `useTheme()` only for raw values; change colors/typography in the theme files.
- **Components:** React Native Reusables (shadcn-style, `@rn-primitives/*`) in `components/ui/`, layout pieces in `components/layout/`, `cn` helper in `lib/utils.ts`. Build higher-level components on these primitives. Without `components/ui/` and `@rn-primitives/*` in `package.json`, compose React Native primitives with NativeWind instead and don't pull `@rn-primitives/*` in unless asked.
- **Icons:** `lib/icons/LucideIcon` wraps Lucide so NativeWind classes apply — `<LucideIcon name="Home" className="h-6 w-6 text-foreground" />`. Don't import from `lucide-react-native` directly, and validate `name` against the wrapper's registry.
- **Portals:** web uses `WebPortalContext`, native uses `PortalHost` from `@rn-primitives/portal`, both set up in `app/_layout.tsx`; the `components/ui/` primitives rely on them.
- **Alias:** `~/*` maps to the project root, e.g. `import { useTheme } from '~/theming/ThemeProvider';`.

Photo retries are offered only on full review/preview surfaces; a transient resolution error is retried a few times (staying in the loading state) before surfacing as "unavailable", so a photo that is merely still loading never shows the failure copy (cloud-only surfaces its iCloud state at once). iOS uses cancellable PhotoKit display-size requests (2048 px, bounded temporary cache), enabling network access for the foreground review and its neighbours (one above, two below, via `network`); decorative requests stay local. Off-screen review photos fail quietly (`quietFailure`, still a loading look) and retry when shown; a discard's next photo waits up to 600 ms (`ARRIVAL_WAIT`) for its picture before the pager scrolls to it. Older binaries retain explicit original-download fallback. Generation guards cancel late results and image callbacks; failed items never qualify encounters. Allowance charging requires loaded foreground/focused media (a video's poster, or its first frame if the poster fails), and failed items do not reserve remaining free slots.
- **Review native media:** `services/review-media.{native,web}.ts` uses `PictopiaReview` helpers in the existing autolinked module. iOS reads and writes PhotoKit `isFavorite` and re-reads after completion; Android 11+ uses `MediaStore.createFavoriteRequest` and verifies `IS_FAVORITE` after OS approval (not a Google Photos cloud guarantee). Earlier Android/browser builds report unsupported; no local substitute. Older classic-review app favorites remain separate. Sharing uses UIActivityViewController with a temporary original-quality resource export (removed after dismissal; unfinished exports cleaned on next share) or Android ACTION_SEND with a granted content URI and no copy. Live Photos share the still resource. Full review surfaces on iOS show the video's own PhotoKit still at display size and true aspect (`videoPoster` in `services/photo-display.*`, via the existing `reviewDisplay`), so the poster lines up with playback; small thumbnails and Android use the cached 160 px platform thumbnail; poster failure never gates playback. `localAssetSize` reads local PhotoKit file URLs / Android MediaStore SIZE, with no network or hash scan. `use-review-video.ts` owns `createVideoPlayer(null)` through `VideoLifecycle`: listener removal and command invalidation precede disposal; queued replacements serialize, pending native work settles before one release, and late callbacks cannot operate on a released player. Review and full preview pause on blur/background; a video's displayed poster qualifies its encounter, review credit and sideways discard exactly like a photo's pixels (first frame is the fallback); playback state never gates discard or credit. `VideoPage` creates its player only while on screen (`useReviewVideo(active)`), classifies failures via `lib/pictopia/video-playback.ts`, and writes sanitized `video.*` diagnostics to the review trace (Adventure Lab export). Native command/source failures become recoverable UI states. Native changes require Publishing; do not claim device validation from host tests.
- Legacy database identifiers and the Live Photo hash boundary marker remain stable across branding changes so existing cleanup data and cached hashes are preserved. Native identifiers are `com.trippinsoft.pictopia` on iOS (registered with Apple) and Android; changing them after release breaks store continuity and local data.
- Native media references are never copies of full-resolution originals. Marking is local only; deletion requires explicit confirmation and OS authorization. Storage numbers are estimates from known sizes, not measured free-space changes.
- Deletion safety (`services/deletion.ts`, rules in `lib/pictopia/deletion.ts`): only items verified visible and unchanged are sent to the OS; a `deletionAttempt` journal is persisted before the request and its OS result after; outcomes (confirmed / remaining / uncertain / skipped) and `confirmedCleanup` are applied in one transaction, processing only still-tracked ids so replays never double count. Absence proves deletion only under full access, or under limited access with a recorded OS success and unchanged scope; everything else goes to `deletionPending`. `recoverDeletions` runs at native startup, on foreground, and before each deletion; it never deletes. Decisions on items in an in-flight journal are refused; restoring/keeping a pending item stops tracking it. Verified deletions set `deletedAt` on the record.
- Swipe decisions and skips pass the displayed item id; the repository rejects them if the session has moved on.
- Copy uses Keep / Set aside / Restore / Delete consistently; counts go through `plural()` in `lib/pictopia/text.ts`.
- Session kept/set-aside numbers shown in Swipe, Home and Insights come from `repository.tally` / `useSessionTally` (current decisions; restored items drop out, verified deletions still count). The `kept`/`marked` fields saved on a session are historical counters, not display values.
- iOS photo purpose strings: read-write access describes browsing, favorites, sharing and confirmed deletion; the add-only string states Pictopia never saves to the library (the key stays because expo-media-library's binary references add-only access).
- **Entitlement:** `lib/pictopia/entitlement.ts` `resolveEntitlement` is the only Pictopia+ decision; screens use `app.pro` from the provider (plus `entitlementSource`), services take that `pro` from callers, and nothing else may call `entitlementActive` or read the stored `entitlement` (guarded by `tests/entitlement.test.cjs`). - **Journey segments and date history:** `services/adventures.ts` keeps one active Yearbook per year and one On This Day journey per local date. Missing year mappings adopt the most recently active meaningful unfinished snapshot; Home, Explore and the year picker expose only that canonical journey, preserving other snapshots and queue marks. Current segments stay under `adventure:<id>:explore`; archived segments use `adventure:<id>:segment:<n>:explore` and canonical queue reconciliation. "Keep going" offers another curated segment (up to 20, final partial allowed) that excludes every photo shown in any earlier segment of that adventure — seen, unqualified or unavailable — so segments never repeat; unavailable items never prove full completion. `lib/pictopia/journey-progress.ts` tracks monotonic 25/50/75/100 recognition on natural segment endings. `app/on-this-day.tsx` lists today plus seven past calendar dates; past-date opening is Pictopia+-only at UI and service boundaries. The shared 100/day gate also covers classic Swipe and full previews. Exit/background flushes the visible fixed slot; highest position remains separate. On This Day is a whole set (not extendable); reopening it, finished or not, returns the same adventure. Opening a finished adventure never auto-starts a new segment.
- **Cloud media boundary:** `services/photo-display.*` and `video-source.*` isolate native retrieval. iOS video plays through the module's cancellable `reviewVideoPlayback(id, token, network)`: local-only unless the user tapped to download (then medium quality); slow-motion/composed videos get one bounded 720p temp export (`tmp/pictopia-video`, 3 kept); older binaries fall back to expo-media-library + `reviewVideoSource`. A Photos library file path is never the first choice: `iosPlaybackSources` hands expo-video `ph://<id>` first (its own loader keeps PhotoKit's access grant), the path as an `alternates` fallback (fetched copy first after an explicit download); Android tries the content URI then the file path. `VideoPage` tries each alternate on a fresh player before showing the failure. Android plays the MediaStore content URI after `mediaService.resolve` proves the item exists. Library indexing restarts (fresh epoch, up to 3 passes, `lib/pictopia/index-retry.ts`) when the library's count changes mid-index. Android currently supports accessible local MediaStore items; a cloud Photo Picker import flow is not integrated. Google Photos full-library enumeration/deletion is not available through this path.
